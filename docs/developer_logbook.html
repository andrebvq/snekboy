Overview

From a crashing Tetris to every DMG acceptance test

SnekBoy 0.1 ran its CPU tests but crashed Tetris, had no cartridge mappers and ran at about a tenth of full speed. Eleven releases later, it passes all 93 DMG-relevant mooneye tests and dmg-acid2, plays every game tested, and runs 5 of 11 at full speed in pure Python.

This logbook records each release: the state of the emulator at the time, what was wrong, how it was found, why the fix matches the hardware, and how the result was verified. It is written for readers who want to learn how the Game Boy works, and how an emulator is checked, from the problems this one actually had.

The release lineSelect a release to open its entry
mooneye tests passed, of 111 (all 93 DMG-relevant tests pass from 0.7) Tetris, frames per second over the first 360 frames, uncapped (60 = full speed); blank where not measured

Two phases

0.2 to 0.7 made the emulator correct. An audit of 0.1 produced the work list. Each release took one hardware area, fixed it against Pan Docs and the test ROMs, and confirmed that nothing else changed. 0.8 to 0.9.2 made it fast without changing behaviour. Every optimisation had to reproduce the previous release instruction for instruction across twelve games.

Blargg: the 33 non-sound ROMs. Speed: Python 3.10, measured by a harness without the window. Releases 0.5 and 0.6 were not benchmarked; they did not target speed.

How to read an entry

0.1 · commit f7cee75

Baseline: the CPU tests pass, the games don't

Version 0.1 implemented every instruction and passed Blargg's CPU tests, yet Tetris crashed when a game started. An audit was run to find out why, and what else was wrong, before any fix was made.

15/33Blargg ROMs
24/111mooneye ROMs
12/13unit tests
~0.1×of full speed

Starting point

The CPU decoded all 245 defined opcodes and 256 CB opcodes. The PPU drew background, window and sprites, and the timer, interrupts, joypad and a simulated post-boot state were in place, with a pygame window, a trace file and Gameboy Doctor logging. The 11 single cpu_instrs ROMs and instr_timing passed.

Gaps that were already known: no memory bank controllers, so only 32 KB ROM-only games could load. Tetris showed its menus and crashed on the transition into a game. The project's own documentation rated the CPU, memory, interrupts and timer as "100%".

How the problems were found

The audit split the code into seven areas: CPU, timer and interrupts, memory and I/O, PPU, integration, crash reproduction, and Python quality. Each area was reviewed separately against Pan Docs and the test ROMs. Every finding needed a script that reproduced it, and then the reviews were cross-checked against each other. Findings by severity:

SeverityFindingsExamples
Crash3Writes to ROM accepted; EI; HALT wild jump; illegal opcodes raise a Python exception
Incorrect behaviour24Echo RAM writes not mirrored; unused I/O bits read 0; signed tiles from the wrong base; LCD off keeps LY counting
Timing accuracy5Timer and PPU advance once per instruction; fixed mode-3 length; no reload-cycle behaviour
Latent8IE overwrite during dispatch ignored; a duplicate, unused decoder
Documentation6The README named a dead file as the timer; comments disagreed with constants

The audit found two misleading "resolved bugs" in the development notes, and both are instructive:

  • "A loop writes 0x2F to 10 consecutive I/O registers" had been treated by making those registers read-only. That loop was the visible end of the Tetris crash (see 0.2), so the patch hid a symptom.
  • "LY stops when the LCD is off" had been "fixed" by keeping LY counting. The original behaviour was the correct one: with the LCD off, LY reads 0 and the PPU is stopped.

The single largest cause of test failures was timing granularity: the timer and PPU advanced once per instruction, after all of its memory accesses. That alone explained every mem_timing failure. It was the hardest fix, so it was scheduled late (0.7), after the local fixes it would otherwise disturb.

Game Boy note: test ROMs as a specification

Hardware test ROMs run on the emulated machine and report their own verdict.

  • Blargg's tests print "Passed" or "Failed" through the serial port, so an emulator can read the result without a screen.
  • mooneye tests signal success by loading the Fibonacci numbers 3, 5, 8, 13, 21 and 34 into B, C, D, E, H and L, and then executing LD B,B.
  • dmg-acid2 draws a face that only comes out right if every PPU rule is right, compared pixel by pixel with a reference image.

Together they turn "behaves like a Game Boy" into a checkable list.

The order of work

  1. Crash first: the memory map (0.2), so Tetris could be played and tested.
  2. More games: cartridge mappers (0.3), so the other test games could load.
  3. Speed to test with: a first performance pass (0.4), because a test run at a tenth of full speed takes minutes.
  4. Accuracy area by area: interrupts and timer (0.5), PPU (0.6), then the timing core (0.7).
  5. Speed with identical behaviour: 0.8 to 0.9.2.

Takeaway

Passing CPU tests says little about a whole system. Most of the defects were in memory, I/O and the PPU, which the CPU tests do not exercise.

0.2 · PR #1 · Memory map

The Tetris crash was the game overwriting its own ROM

A harmless write to address 0x2000 was stored over the ROM, which turned a loop's jump into a different instruction. Making ROM read-only fixed the crash. The release also made memory and I/O behave as on a DMG.

16/33Blargg +1
28/111mooneye +4
20/20unit tests
PlaysTetris, through game over

How it was found

The crash reproduction scripted the button presses into a game and traced backwards from the runaway program counter. The chain:

  1. At PC 0x0254, Tetris executes LD (0x2000),A with A = 1. On a cartridge with a mapper this selects ROM bank 1. Tetris has no mapper, so the write should do nothing.
  2. SnekBoy stored the byte. ROM address 0x2000 changed from 20 to 01.
  3. That byte belongs to a fill loop: JR NZ,-4 now decoded as LD BC,0x19FC.
  4. The loop never stopped. It wrote 0x2F through work RAM, I/O, high RAM and IE, which is the "0x2F in 10 I/O registers" symptom from the old notes.
  5. A jump table then read state 0x2F, and the PC ran through echo RAM to 0xFE00.
ROM at 0x1FF8
0E023E2F060A220520FC190D
After the write
0E023E2F060A220501FC190D

A patch that ignored writes below 0x8000, and changed nothing else, ran 2,600 frames to a normal game over. That confirmed the cause before the real fix was written.

Changes

ROM is read-only

Hardware
0x0000-0x7FFF is ROM. Writes there go to the mapper chip, if the cartridge has one. A ROM-only cartridge ignores them.
SnekBoy
Stored the write in the ROM image.
Fix
Writes to the ROM region are dropped. From 0.3 they go to the mapper.

Echo RAM and the unusable area

Hardware
0xE000-0xFDFF mirrors work RAM at 0xC000-0xDDFF for reads and writes. 0xFEA0-0xFEFF is not usable: on DMG it reads 0x00, and writes do nothing.
SnekBoy
Mirrored reads only, and treated 0xFEA0-0xFEFF as RAM.
Fix
Both mirrored; the unusable area ignores writes and reads 0x00 (0xFF while OAM is locked). This also stopped three mooneye ret*_timing tests running away, because they returned through an echo address.

Unused bits read as 1

Hardware
Bits that an I/O register doesn't implement are not driven, and read as 1. IF reads 0xE0 | flags, and an unmapped register reads 0xFF.
SnekBoy
Returned 0 for them.
Fix
Each register has a mask that is ORed into reads. Blargg's halt_bug passed at once: it checks IF, and IF's upper bits had read 0.

Illegal opcodes, FF50, post-boot values

Hardware
The 11 undefined opcodes (D3 DB DD E3 E4 EB EC ED F4 FC FD) hang the CPU, while the timer and LCD keep running. After the boot ROM, P1 reads 0xCF and DIV is 0xAB.
SnekBoy
Raised a Python exception and quit. The FF50 handler sat behind a filter and could never run. DIV was set to 0xAB, but its internal counter started at 0, so DIV dropped to 0 on the first cycle.
Fix
The CPU locks up and prints the opcode once; FF50 is reachable; the counter itself is seeded so that DIV reads 0xAB.

Game Boy note: DIV is a view of a counter

DIV (0xFF04) is the upper 8 bits of a 16-bit counter that advances every T-cycle. Setting "DIV = 0xAB" really means setting the counter to 0xAB00 plus some phase. The same counter drives the timer, serial and other circuits, which is why its exact value matters later (0.5, 0.7).

Verification

Check0.10.2
Unit tests12/1320/20
Blargg1516 (halt_bug)
mooneye2428 (boot_hwio, unused_hwio, if_ie_registers, mbc2/bits_unused)
TetrisCrash on starting a gamePlays; level transitions work (checked by hand)

Takeaway

Where a crash shows up can be far from its cause. The visible damage, I/O registers full of 0x2F, was three steps downstream of one wrong write. Tracing backwards from the damage finds the cause; patching the damage hides it.

0.3 · PR #2 · Cartridge mappers

Bank switching lets games larger than 32 KB run

Only 3 of the 12 test games reached their title screen, because the rest need a memory bank controller. 0.3 added MBC1, MBC2, MBC3 with its real-time clock, and MBC5, plus battery saves. A one-line PPU bug that scrambled several games was fixed along the way.

17/33Blargg +1
53/111mooneye +25
27/28mooneye MBC tests
12/12games reach their title

Changes

Memory bank controllers

Hardware
The CPU sees only 32 KB of ROM: bank 0 at 0x0000-0x3FFF and a switchable bank at 0x4000-0x7FFF. A mapper chip on the cartridge chooses that bank, and the RAM bank at 0xA000-0xBFFF, when the game writes to the ROM range. The cartridge type at header byte 0x147 says which chip is fitted.
SnekBoy
Had no mappers, and copied any ROM flat over the address space, up to 64 KB over 0x8000-0xFFFF.
Fix
Mappers in src/cartridge.py, chosen from the header. A switch copies the new 16 KB bank into the memory array, so the very frequent ROM reads stay a plain array index and only the rare switch pays.

Game Boy note: MBC1 in four registers

Write toEffect
0x0000-0x1FFFRAM enable: low nibble 0xA enables, anything else disables
0x2000-0x3FFFLow 5 bits of the ROM bank; a value of 0 selects 1
0x4000-0x5FFF2 more bits: upper ROM bank bits or the RAM bank
0x6000-0x7FFFBanking mode: whether those 2 bits also apply to 0x0000-0x3FFF and RAM

MBC3 adds a real-time clock. Writing 0 then 1 to 0x6000-0x7FFF latches the time into readable registers. Tetris's write of 1 to 0x2000, the cause of the 0.2 crash, is an MBC1-style bank select that its ROM-only board ignores.

Signed tile numbers count from 0x9000

Hardware
With LCDC bit 4 clear, background tile numbers are signed (-128..127) relative to 0x9000, which covers 0x8800-0x97FF.
SnekBoy
Used 0x8800 as the base, shifting every tile by 128.
How found
The audit's dmg-acid2 diff, and scrambled title screens in Super Mario Land and Dr. Mario once they could load. It was planned for the graphics release and pulled forward.

STOP, and cartridges that under-declare RAM

Hardware
On DMG, STOP resets DIV and halts the CPU and timer until a button is pressed.
SnekBoy
Acted on KEY1 (0xFF4D), the Game Boy Color speed switch. The combined cpu_instrs ROM reached STOP with no wake source and hung.
Fix
DMG STOP. Separately, cartridge types "with RAM" whose header gives RAM size 0 now get 8 KB, as other emulators do; Blargg's halt_bug needs it.

Battery-backed RAM is loaded from <rom>.sav at start and written on quit, with the MBC3 clock in <rom>.rtc.

Verification

Unit tests 20 → 32, covering banking per mapper, RAM enable, the clock and saves. The combined cpu_instrs (a 64 KB MBC1 ROM) passes. mooneye's MBC set went from 1 to 27 of 28; the remaining one is the MBC1 multicart wiring, used only by compilation cartridges.

Takeaway

Choose the data layout for the common operation. Copying 16 KB on a bank switch looks wasteful, but a game switches banks hundreds of times a second and reads ROM millions of times.

0.4 · PR #3 · Speed, part 1

Profiling first: the PPU and display cost more than the CPU

At 4.5 frames per second, testing a game took minutes. A profile showed that most of the time went to drawing, not emulating. Three changes doubled or tripled the speed, and the output stayed pixel-identical.

9.6Tetris fps (was 4.5)
15.9Super Mario Land fps (was 5.2)
12/12games pixel-identical

Changes

The PPU reads video memory directly

Found
The PPU fetched every tile byte through Memory.read_byte, which applies the CPU's access rules, once or more per pixel.
Fix
The PPU reads the memory array directly. A table of 65,536 entries maps each pair of tile bytes to its 8 colour numbers, so a tile row costs one lookup. This also fixed Gameboy Doctor mode freezing the picture: its fake LY value, meant only for the CPU, had been reaching the PPU.

Game Boy note: 2 bits per pixel, split across two bytes

A tile is 8×8 pixels in 16 bytes. Each row is two bytes: the first holds the low bit of each pixel's colour number and the second the high bit, with bit 7 as the leftmost pixel. The colour number (0-3) then goes through a palette register (BGP, OBP0, OBP1) to one of four shades.

Fast reads, and one call per frame for the display

Found
Plain ROM and RAM reads went through every special-region check. The Gameboy Doctor setting was read from the environment on every LY read. The display drew 23,040 pixels with one pygame call each.
Fix
ROM, work RAM and high RAM return early. The setting is read once. The frame goes to pygame as one block of colour numbers on an 8-bit surface with a 4-entry palette.

Verification

This release introduced the comparison method used for every later release. Before any change, a script recorded CPU registers, cycle count and a hash of the screen for 12 games every 30 frames, over 600 frames. After each change, the same run had to give identical fingerprints. Blargg and mooneye results stayed at 17 and 53.

Takeaway

Measure before optimising. The obvious suspect, the CPU, was not where the time went.

0.5 · PR #4 · Interrupts and timer

Interrupts and the timer, down to the edge cases

The basics worked, but mooneye's tests for the order of events failed: when EI takes effect, what happens when DI follows it, when an interrupt is chosen, and how the timer reacts to writes. Each was fixed against the specific test that probes it.

62/111mooneye +9
42unit tests (was 32)
12/12games pixel-identical

Changes

EI and DI

Hardware
EI enables interrupts after the next instruction. DI disables them at once and cancels a pending EI. A second EI does not restart the delay.
SnekBoy
Let EI; DI through an interrupt, and restarted the delay on EI; EI.
Tests
mooneye rapid_di_ei, ei_sequence.

Dispatch can be cancelled by its own push

Hardware
Dispatch takes 5 M-cycles: two internal, the push of PC's high byte, the push of the low byte, then the jump. The interrupt is chosen after the high byte is pushed. If SP was 0x0000, that push writes to IE (0xFFFF) and can remove the interrupt being dispatched, and the CPU then jumps to 0x0000.
Tests
mooneye ie_push.

EI followed by HALT

Hardware
When HALT runs with IME clear and an interrupt already pending, the CPU doesn't halt, and the next byte is read twice (the HALT bug). After EI; HALT, IME is set by the time the interrupt is serviced, so the handler returns to the HALT itself.
SnekBoy
Applied the HALT bug to the handler's first instruction instead, which made it jump wildly. This was one of the audit's three crash-class findings.

The timer is an edge detector

Hardware
TIMA ticks on the falling edge of one bit of the system counter (bit 9, 3, 5 or 7, chosen by TAC) ANDed with the enable bit. So any write that drops that signal from 1 to 0 also ticks TIMA, such as resetting the counter through DIV.
SnekBoy
Reset DIV without the edge.
Tests
mooneye's four *_div_trigger tests.

Game Boy note: the overflow cycle

When TIMA overflows, it reads 0x00 for one M-cycle. Only in the next M-cycle is TMA copied in and the timer interrupt requested. Writing TIMA during the first cycle cancels the reload. During the reload cycle, a TIMA write is ignored and a TMA write goes through to TIMA (mooneye tima_write_reloading, tma_write_reloading).

Also removed: src/timer.py, an unused module that the README had presented as the timer. The real timer had always been in cpu.py.

Takeaway

For interrupt logic the order of events is the specification. Each fix here moves one action by one M-cycle or one step in a sequence, and each has a test ROM that tells the two orders apart.

0.6 · PR #5 · Graphics

dmg-acid2 from 818 wrong pixels to zero

The PPU drew most games acceptably, but dmg-acid2 differed from its reference in 818 pixels. Wario Land II stopped at a white screen after its intro. The fixes cover the window, sprite priority, LCD on/off and the STAT interrupt line.

0wrong acid2 pixels (was 818)
66/111mooneye +4
53unit tests

Changes

The window has its own line counter

Hardware
The window keeps an internal line counter that advances only on lines where the window was actually drawn. If a game hides the window for some lines, it resumes where it left off rather than at LY − WY. It is also hidden when LCDC bit 0 is off, and for WX below 7 it shifts left rather than clamping.
How found
The dmg-acid2 difference, which the audit traced to the missing counter.

Sprite priority uses colour numbers

Hardware
A sprite with the "behind background" flag is hidden only where the background's colour number is 1-3, whatever the palette makes that look like. Where sprites overlap on DMG, the one with lower X wins, then the lower OAM index, even when the winner is itself hidden by the background.
SnekBoy
Compared the final shade, and let later sprites draw over earlier ones.

LCD off stops the PPU

Hardware
With LCDC bit 7 clear, LY reads 0, the mode is 0, no LCD interrupts fire and the screen is blank. Turning it on restarts at line 0, and the first line has no OAM-search period.
SnekBoy
Kept LY counting and interrupts firing. This was the earlier "resolved bug" that the audit flagged as wrong.

The STAT interrupt fires on a rising edge

Hardware
The four STAT sources (HBlank, VBlank, OAM, LY=LYC) are ORed into one line, and the interrupt is requested only when that line goes from 0 to 1. If one source is already active, a second becoming active requests nothing. This is called "STAT blocking".
SnekBoy
Fired once per source on entry.
Also
STAT writes keep the read-only bits; an LYC write re-checks the match; line 153 reads LY 0 after its first few dots.

Verification

The method gained screens with input: 11 games driven by scripted button presses, 20 screenshots each, compared with 0.5. Wario Land II now continues past its intro. The other games differed only by about a frame of timing, which is expected when interrupt timing changes. Blargg stayed at 17.

Takeaway

A reference image catches what a "looks right" check misses. Most of the 818 pixels were in places a player would never notice, and each traced back to a real rule.

0.7 · PR #6 · Timing

Every memory access on its own cycle

The largest finding of the audit: the timer and PPU advanced once per instruction, after all of its memory accesses. 0.7 places each access on its own M-cycle and brings the timer, PPU and DMA up to that cycle before any access that can see them. All DMG-relevant mooneye tests passed afterwards.

26/33Blargg +9
93/111mooneye +27
65unit tests
−5%speed, the cost

The problem

LDH A,(0x05) reads TIMA. It takes 3 M-cycles: fetch the opcode, fetch the operand, read the register. On hardware the read happens in the third M-cycle, so it sees the timer as it is 8 T-cycles into the instruction. SnekBoy ran the whole instruction and then advanced the timer by 12, so every read saw the state from the instruction's start.

Blargg's mem_timing tests measure exactly this, and they all failed. So did mooneye's instruction-timing tests, which time pushes and calls against the timer.

Changes

Per-access catch-up

Design
Each instruction counts its M-cycles as it goes: fetches, reads, writes, and the internal delays in PUSH, CALL, RST, RET cc and dispatch (_acc). Before any access that can observe another component (I/O, VRAM, OAM, or anything during DMA), the timer, PPU and DMA catch up to that access's cycle (_synced). The rest is advanced when the instruction ends.
Why
Advancing every component after every M-cycle would also be correct, but several times slower. Catching up only before an observable access gives the same results, because nothing else can tell the difference.

Real OAM DMA

Hardware
A write to 0xFF46 starts a copy of 160 bytes to OAM, one byte per M-cycle after one setup cycle. The CPU keeps running but can use only high RAM; OAM reads 0xFF. A new write restarts the copy. Sources 0xE0-0xFF read work RAM.
SnekBoy
Copied instantly and added 640 cycles to the clock.

The pixel-transfer length varies

Hardware
Mode 3 lasts 172 dots plus the fine X scroll (SCX mod 8), 6 dots if the window starts on the line, and a stall for each sprite (6 dots, plus up to 5 depending on its position within a background tile). HBlank starts later by the same amount, and games timing raster effects depend on that.
Also
LY shows the next line 4 dots early; the OAM and VRAM locks change on their own dots around modes 2 and 3.

Serial and joypad interrupts

Hardware
An internally clocked transfer shifts one bit per falling edge of system-counter bit 8 (8192 Hz), then raises the serial interrupt. The joypad interrupt fires when a selected P1 line goes from 1 to 0.
SnekBoy
Never raised the serial interrupt; raised the joypad interrupt on any key, selected or not.

Found during verification: an LYC=0 double interrupt

Symptom
Final Fantasy Legend stopped at a white screen with the new timing.
Cause
LY reads 0 from early in line 153 through line 0. The new "LY=LYC reads 0 at the end of a line" rule cleared the flag between those two lines, so an LYC=0 STAT interrupt fired twice. The game took the second one inside its own handler and never reached its title.
Fix
The flag carries from line 153 into line 0.

What still fails, and why

FailingReason
17 mooneye boot and register testsThey check the power-on state of other models (DMG0, MGB, SGB, CGB, AGB). SnekBoy is a DMG-ABC.
mooneye multicart_rom_8MbMBC1 multicart wiring, not implemented
Blargg oam_bug (6 of 9)The DMG OAM corruption bug is not emulated

Takeaway

Synchronise lazily, but exactly. A component only has to be up to date when something can observe it. Identifying every observation point is what makes this correct, and it became the basis of the performance work in 0.9.1.

0.8 · PR #7 · CPU speed

Three times faster, with every state identical

With accuracy in place, speed became the problem: Tetris ran at 8.8 fps. Four profiled steps took it to 28, and each step had to reproduce the previous one exactly.

Method

  1. Measure first: 120 frames under cProfile, sorted by each function's own time. Every change was picked from that list.
  2. Freeze a reference before touching code: state fingerprints of 12 games and screenshots of 11, recorded from a clean copy of 0.7.
  3. One change per step, then prove nothing moved: unit tests, fingerprints, screens, the test ROMs and dmg-acid2.
  4. A test per shortcut: it compares the fast path with the original logic on random input, so a later edit can't drift silently.

Counting timer edges instead of looping

Idea
The number of falling edges of counter bit k between values old and new is (new >> (k+1)) − (old >> (k+1)). A batch of N cycles costs one subtraction, not N loop iterations.
Exact path kept
While an overflow or reload is in progress, during a serial transfer, or when the batch itself would overflow TIMA.

A dispatch table derived from the decoder

Idea
At start-up, each opcode is decoded once with probe fetch functions. They record whether a byte or word is fetched and return a marker object; wherever the marker lands is where the real operand goes at run time. The table holds (handler, operands, operand kind, slot, cycles).
Why derived
Writing 500 handlers by hand would risk new bugs. Deriving the table from the existing decoder keeps fetch order and cycle counts identical by construction, and a test checks every opcode against the decoder.

Python note: what costs time

In CPython, the expensive operations are function calls and attribute lookups, not arithmetic. A flag write that went through a property, a helper, an Enum lookup and a bit-field class cost four calls; a mask on one integer costs none. Most gains in 0.8 to 0.9.2 come from removing calls per emulated instruction.

Why Tetris gained more than Super Mario Land: Tetris busy-waits. In 120 frames it executed about 290,000 each of LDH, AND and JR out of 893,000 instructions: almost all of them are the loop ldh a,(STAT); and 3; jr nz, so cheaper instructions help it directly. Super Mario Land sits in HALT, and a halted CPU still cost one timer and PPU call per idle M-cycle. That became the target for 0.9.

Takeaway

Optimise against a frozen reference. "It still looks fine" doesn't prove anything; identical registers, cycle counts and screens do.

0.9 · PR #8 · Handlers and HALT skip-ahead

A halted CPU jumps to the next event

Two changes, one for each kind of game. Dedicated handlers sped up busy-waiting games; skipping idle time sped up games that wait with HALT, Super Mario Land by three times. Six of 11 games reached full speed.

116Super Mario Land fps (was 36)
36.1Tetris fps (was 29)
6/11games at full speed

Changes

Dedicated handlers from templates

Problem
After 0.8, handlers still received operand names as text ("B", "(HL)", "NZ") and resolved them on every call.
Fix
src/fast_ops.py generates 439 functions from templates (loads, 8-bit ALU, INC/DEC, jumps, calls, returns, LDH, all CB operations). Each has its register or condition written in and computes all four flags as one byte expression, for example AND: f = 0xA0 if res == 0 else 0x20.
Test
Each dedicated handler against the generic one on 40 random states: registers, flags, memory, the bus timing and the returned cycles. A planted half-carry bug, and a removed internal cycle in RET cc, both made it fail.

HALT skip-ahead

Insight
The PPU changes state only at fixed dots (76, 80, the end of mode 3, 452, 456, dot 4 of line 153), and it reads nothing a halted CPU can change. So advancing it 1,000 cycles at once gives the same result as 250 steps of 4. The only thing to protect is when the CPU notices an interrupt.
Fix
A halted CPU advances to the earliest of the frame's end, the next PPU event, or the cycle where TIMA overflows: ((c >> s) + 256 − TIMA) << s for counter c and rate shift s. It falls back to single M-cycles during DMA, serial, or a TIMA reload.

A stricter check: instruction traces

Skipping changes how often step() is called, so the verification gained a rolling SHA-1 over every executed instruction's cycle count and registers, with halted M-cycles left out. One instruction executed a single cycle early changes every later hash.

Found during verification: the cartridge clock

Symptom
Pokémon Gold's trace differed from the very first chunk, while its states and screens matched.
Cause
Re-running the unchanged 0.8 now gave the new trace too. Gold's MBC3 clock reads the host time, so its registers depended on the time of day.
Fix
All harnesses freeze the host clock. Any input from outside the emulator (time, buttons, save files) must be pinned for a comparison to mean anything.

Small items

  • Fixed frame ends: the frame loop used to drop the few cycles the last instruction ran past each frame, so emulated time ran about 0.02% slow. Frame ends are now fixed multiples of 70,224.
  • Version in the window title, read from a single src/version.py.
  • Palette: in the widely used green palette, shade 1 is almost as light as shade 0, so light-grey detail nearly vanishes. The new default keeps shades 0, 2 and 3 and puts shade 1 halfway, giving even steps. P switches between green, classic and grey. A real DMG's reflective LCD has no exact colour; every palette is an approximation.

Takeaway

Find the invariant that makes a shortcut exact. "The PPU is batch-invariant, and only the interrupt points matter" turned an approximation into an exact skip.

0.9.1 · PR #9 · Lazy sync

Bring the timer and PPU up to date only when someone looks

In the slower games, about 40% of the time went to advancing the timer and PPU after every instruction, although nothing could see them change. 0.9.1 lets the CPU owe them cycles until an access, an interrupt point or the end of the frame.

−92%PPU update calls (Kirby)
+12–22%speed of busy-waiting games
0changed results

Idea

A running CPU can observe the timer and PPU in only three ways:

  1. Through an I/O, VRAM or OAM access. These already caught up before the access, since 0.7.
  2. Through an interrupt, which is raised only at a PPU event or a TIMA overflow.
  3. At the end of a frame, when the screen is shown and buttons are read.

So the cycles of other instructions can be owed until one of those points.

Implementation

Owed cycles
_lag is folded into the existing catch-up bookkeeping at the start of each instruction. Every existing catch-up then pays old and new cycles together, with no new code paths.
Budget
The cycles until the next point where an interrupt could be raised, from dots_to_next_event() (built for the HALT skip) and the TIMA overflow formula. Landing exactly on an event must sync, so the comparison is strict.
Resets
A write to 0xFF00-0xFF7F resets the budget, because TAC, LCDC, LYC, STAT and DIV can move the next event. During DMA, serial or a TIMA reload the budget is 0, and syncing happens every instruction as before.

Testing it properly

A random-program test compares the lazy frame runner with plain stepping: registers before every instruction, and timer, PPU and screen at the end. Its first version caught none of four planted bugs. The programs read I/O so often that the existing catch-up hid every late sync. Adding delay loops without I/O, as real games have, made the test strict. The stricter test then found a real bug: on an illegal opcode the owed cycles were dropped.

Tried and rejected

Idea
A longer budget that skips the PPU events which can't raise an interrupt.
Result
Correct, but only about 3% faster. Not worth a second correctness argument, so it was reverted. The budget length was not the bottleneck; the number of calls per instruction was.

Takeaway

A test that can't fail proves nothing. Planting bugs on purpose (mutation testing) showed that the first test was blind, and why.

0.9.2 · PR #10 · Frame loop

One inline loop per frame

After the lazy sync, most of the remaining time was per-instruction overhead: about five method calls and dozens of attribute lookups for values that don't change during a frame. 0.9.2 runs the common case in one loop, with those values in local variables.

51.4Kirby gameplay fps (was 38.7)
65.9Zelda DX gameplay fps (was 53.2)
5/11games at full speed in gameplay

A better benchmark first

Testing 0.9.1 by hand, games felt slower once in play than the benchmark suggested. The benchmark covered the first 360 frames, mostly intros and title screens. A gameplay benchmark now presses Start and A to get into the game and measures frames 700-1200. Pokémon Red, for example, ran at 83 fps in its intro but 45 in gameplay. Both numbers are reported from 0.9.2 on.

Change

The inline frame loop

Fast path
While the CPU is running, PC is in ROM, work RAM or high RAM, no DMA runs and no interrupt is due, one loop does everything inline. It checks interrupts, reads the opcode and operands straight from the memory array (with the same per-access timing as the bus), calls the handler, counts down EI and does the lazy-sync accounting.
Fallback
Anything else uses the existing step() for that one instruction: halted, stopped, locked, the HALT bug, DMA, PC elsewhere, interrupt dispatch, an illegal opcode. The rare cases keep their verified code.
Hook
_on_instruction is called before each instruction when set. The instruction-trace harness uses it, so it checks the fast loop itself rather than step().

Testing

The random-program test gained 16-bit-address accesses to I/O registers, and it now also compares when each I/O access happens inside its instruction. That second addition was needed: a planted bug that put a word operand's read 4 cycles early passed the state comparison. A 4-cycle shift changes the outcome only when an event falls inside those 4 cycles, which is rare in random programs. All five planted bugs now fail the test.

Gameplay fps0.9.10.9.2

Busy-waiting games gained most. HALT-heavy games changed little, because their time is in halted stretches, which still go through step(). Run-to-run noise is about ±5%.

Takeaway

Benchmark what users do. The intro benchmark was accurate but not representative, and a user's remark exposed it.
